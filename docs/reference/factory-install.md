# abe install

`abe install`: how Abe sets a repo up for the Factory, part by part.

## Factory install

ADR 0011. `abe install [--repo <main checkout>]` sets a repo up for the Factory in one chat: it opens the repo's Abe chat on `/abe:install` (starting it, or reopening it), kept per main checkout (`<state>/installs/<hash>/install.json`; a worktree is refused `not-main-checkout`; no record: `no-install`). The Board offers a repo `no-install` says is not in the Factory one header note for a developer: `Not in the Factory yet · Install ⏎` while its board is not read (⏎ runs `:install`), else `· :install`. The install is a set of parts, each with a check, not a sequence of stages: it is Done when every required part passes (`abe install check --all`). The Abe chat follows one skill as a guide, `core/skills/install/` (`INSTALL_SKILLS`, in the Abe chat's plugin, not a Factory run's): the parts table, where things go, how to work, and a reference per part (`references/<part>.md`) it loads before working on that part, Read's findings in `references/read.md`. The main chat talks and coordinates; the heavy work runs in subagents: Read, `env-map`, fixing a failing check, and the Verification pack, started in the background as soon as the app runs locally. Questions go through AskUserQuestion: one up-front round (where the board is, where cards run, who merges and when a card is Done, where specs go, each environment's aws profile, the sources), each answer preselected from evidence, every question offering "Not sure: find out" (the agent then searches the team's sources read-only, cites what it found, and asks again later), then one question at a time as the work raises them. The agent does whatever the person asks itself (adds an MCP server and starts its sign-in, edits an env file, adds a check); only a login in the person's browser or terminal is theirs (it gives the exact `! <command>`), and prod on for agents comes only after a confirm question. Rules in `core/src/install/install.ts`, `install-read.ts` (Read), `install-gate.ts` (the gate); the view every client draws is `core/src/install/install-view.ts` (`InstallView`), sent as the `install.changed` event on each change. Commands in `serve/src/install/install.ts`: each part's reads beside core's verdict on them in one table (`PART_CHECKS`; the verdicts in `core/src/install/install-parts.ts`, the reads passed in as data). One owner per checkout changes the record (`serve/src/install/record.ts`): each change loads, moves and saves it after every change asked before it, its reads done before on the record as it was, so two at once never lose one another's; the sources' sign-ins serve runs are its state too, never the record's. IO in `ports/src/git/install-repo.ts` (`InstallRepo`, `InstallStore`).

- **The parts**, in hint order: `logins` (every tool the repo needs answers, az only for an Azure board, and the live read of GitHub and the cloud is right), `board` (`abe.yaml` names a board that reads live, where cards run, who merges, when a card is Done and where specs go), `sources` (optional: each source found is added and reads, or is skipped), `env-files` (the team's since ADR 0040: `abe.yaml` places each of the repo's env files, in `worktree:` groups or `env.notUsed`, `env-not-in-abe-yaml` else; and the person's own, failing on a join too, `PartVerdict.personal`: the three Abe env files exist, prefilled from `abe.yaml`'s groups when it places them, and each environment has an aws profile or none, prod off for agents unless the person turned it on), `worktree` (`abe.yaml` has the worktree recipe, `worktree: {}` when the defaults are enough; a throwaway worktree of HEAD made ready by it, `InstallRepo.tryWorktree`, has each listed path and its script passes; an env file placed (`abe.yaml`'s groups, then the env map) in an environment on that no copy brings warns, `worktreePart`), `checks` (every check in `checks:` passes as serve runs it, in the checks env), `skills` (the repo's testing skill and `CLAUDE.md`), `verify` (the app runs locally through the gate, or the person chose "can't run here"; the Verification pack exists and proves a feature; the checks pass again after the pack is written, so lint covers its scripts), `prototype` (optional, for a repo with a web app: `abe/scripts/prototype-start` starts it for a prototype; its check, `install-prototype.ts` and `serve/src/prototype/prototype-try.ts`, starts it as a prototype's in a throwaway worktree and goes step by step, script · start · ready · page · login · screenshot, each refused with its code: `no-start-script`, `start-script-not-executable`, `login-key-missing`, `env-not-ready`, `start-failed`, `start-timeout`, `no-url`, `port-not-base`, `not-ready`, `no-page`, `login-failed`, `no-screenshot` (a warning); then stops it; the try kept as the status's `prototype`: steps, URL, port base, the start's log and the screenshot, `<state>/prototypes/install-check/`), `done` (every required part passes; its line names the changed files to commit, `git status` of `abe.yaml`, `abe/` and `.claude/skills/`). The connection's live read runs inside the logins, board and sources checks, and Run locally's gate inside verify's. Each part's check is what ended its stage before; only the gating is gone.
- **Files**: `abe.yaml` at the repo root is the team's (board, where cards run (`serve.target`: yours for the repo over it, yours on this machine where it says none), when a card is Done (`factory.done`: an environment's name, or `merged`; a run always ends in a pull request), environments, checks, setup, spec, overrides and `sources:`), and `.claude/skills/<name>/` holds the repo's skills, the app's scripts (`run-app/scripts/{start,stop,seed,db}`, with `run-app/SKILL.md`: how the app runs locally; `abe run <name>`, prototype start, the gate and box sync read them there) and the Verification pack. Both are written as ordinary files: Abe never commits them and never puts them in `.git/info/exclude`; they show in `git diff`, and the person commits and pushes. `.abe/` is local only and always in `.git/info/exclude` (it holds secrets): the Abe env files, `.abe/settings.local.yaml` (yours: `logins: { gh, az }`, `credentials: { <env>: { awsProfile } }`, overrides) and Abe's local records and scratch. The env-file mapping is never shared: each person's is built from evidence by `install env-map`. There is no kind: Local only and Connected are gone, and what they decided is plain settings in `abe.yaml`: `board`, its `provider` field (`local` or `azure`; GitHub Projects and Jira have no cards yet; `abe settings get board` reads it, `board.provider` is no setting of its own) and `serve.target` (`local` or `cloud`). An old install's `abe.yaml` and `.claude/skills/` are not read.
- **Join**: on a repo that has an `abe.yaml` (a teammate's install), the status says `join: true` and the session does only the personal parts: logins, env files, the aws profiles, the MCP sign-ins. A failing team part is a warning (`warn`), not a blocker.
- **Commands**: `abe install status [--json]`: the repo, `join`, its Abe chat (`id`, `state`), each part (`required`; `state` `pass`, `warn`, `fail` or `todo`; its `line`, one sentence: what passed, or what is missing and the fix; `checkedAt`) and `done`, and `read`, Read's findings (names, paths and keys, never a value; null before Read). `abe install gate` answers its own `gate` result first, then the status. The Abe chat's `abe run <script>` runs in the main checkout (the gate's `abe run start`); `install try` runs checks only and says so. `abe install check <part>|--all [--json]`: serve validates the part now, from the files, settings and live reads, and records its state, line and time; exit 0 on pass or warn, 1 on fail (the `ok` envelope is false only when it can't run). `abe install try <check-name>|--command "<cmd>"`: runs a repo check as serve does (below). Kept as tools the skill calls: `install env-map`, `install env-profile`, `install checks-env`, `install connection`, `install gate`, `install logins`, `install sources`, `install source <name> [--url]` (writes `abe.yaml` `sources:`), `install reset`. Gone with the stages: `install form`, `stage-done`, `rerun`, `again`, `answer`, `env-place`, `board-where`, `kind`. The Abe chat may run every abe command, prod on for agents included.
- **Read** (`readCheckout`): local files only (`READ_FILES`, `.github/workflows/*`, `docs/*.md`, `*.tf` at the top and in `terraform/` and `infra/`; a monorepo's workspaces from package.json's `workspaces`, `pnpm-workspace.yaml`, else the folders at the top two levels holding a package.json, never node_modules, dist or build: each one's package.json, env example and Serverless / CDK config, and the shell scripts package scripts and CI run, bounded, a cap reached in `capped`) and the `board` setting in force: CI's commands, the env example's keys (never values), the logins needed (github, claude; az for an Azure board or Azure CI; aws when the repo uses it: `aws`, each place with its file and line, from the aws SDK, CDK, Terraform's aws provider, Serverless, an aws CI step, `AWS_*` keys, the repo Layer's `logins:` or an aws source; `awsProfiles`: the named profiles scripts and CI use, `--profile x`, `AWS_PROFILE=x`, a Serverless / CDK `profile:`, a script's argument at its callers, each with file and line, never put in `logins:` by Read), each workspace's scripts, test scripts, env example keys and stack, ports an auth callback fixes, the repo's sources (`install-sources.ts`: each MCP server `.mcp.json`, `.claude/settings*.json`, `.cursor/mcp.json`, `.vscode/mcp.json` name, and hints from dependencies, top-level config files, docs links and env keys; each with what it is and why, its file and line), the env files with cloud credentials (`read.cloudCredentials`, `cloudCredentialsWhy`: aws in the name, or `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` among its key names, which serve reads, never a value; never read by a session, like `neverRead`, tracked or not), the env files of public keys alone (`read.publicEnv`, by the same key names and `publicEnvOnly` below: readable, so the view leaves them out of `neverRead`), its kind (ADR 0026, `install-kind.ts`: web app, service, config as code, infrastructure as code, library, CLI, or a monorepo of these per workspace, each with the files that say so; its deploy tools (a CI command that deploys, terraform's `apply`, never `init`, `plan` or `validate`; else the tool's own file), outside systems, fixed ports, template placeholders and each environment's mapping file, the static checks for it, each that runs none of the repo's code run once on a clean tree of HEAD (`InstallRepo.runChecks`: `git archive` into a temp folder, the person's environment left out) with the failing ones moved to `failing`, the paths never read; config templates and Dockerfiles in the top, `KIND_DIRS` and the workspaces read, never a rendered config, an env file or a gitignored one) and what a merge deploys (`install-deploys.ts`: CI jobs that deploy on a push to main or master, each environment and whether it is prod), and `read.originAbe`, origin's default branch when it tracks a `.abe/` HEAD does not track the same (`InstallRepo.originOnly`, refs as fetched last): the agent says it is older (a teammate's or an earlier install's), card worktrees get this install's, the tracked one stays as it is.
  The agent writes the board to `abe.yaml` itself: `board: { provider: github }` for the repo's GitHub Issues (origin's repo; offered first when origin is on GitHub and the repo names no Azure board), `board: { provider: local, project: <repo folder> }` for a board on this machine (keeping `types`), or `board: { provider: azure, organization, project, team }` read from an Azure Boards URL (below).
  Read names the boards the repo names (`read.boards`, `install-board-hints.ts`): an Azure DevOps origin's organization and project first (`azureRemoteOf`, `why: origin`), then each link to Azure Boards (dev.azure.com, visualstudio.com), GitHub Projects (`github.com/orgs|users/<o>/projects/<n>`) and Jira (`<site>.atlassian.net`: an issue, a board, a `projectKey`) in CLAUDE.md, AGENTS.md, the README, docs and CI (Actions, `azure-pipelines.yml`), in that order, then an Azure DevOps org and project said in prose (`boardHintsIn`, `why: <file>:<line>`; one hint a board, its link with a team kept), and a GitHub origin's issues last (`github-issues`, `withOriginHint`, `why: origin`). The board part offers the first Azure one for **Another Azure board**. `azureBoardOf` reads any Azure Boards URL's org, project and team: a team board (`…/_boards/board/t/<team>`), a backlog or sprint (`_backlogs/backlog/<team>`, `_sprints/taskboard/<team>`), an older link with the team in its path, a query or a work item (no team: the project's default team, `<project> Team` (`defaultTeam`), which the Connection check's Board fact says).
  serve reads the board the repo's settings name with the board login (az signed in): refused (401, 403), it is not in force and the agent asks for the board again (`unreadable`, `board` null). The view's `boardProposal` says why and offers another the repo names (`said`: "The repo's settings name <org>/<board>, which your az login can't read (401); the repo's CLAUDE.md:3 names Azure Boards <org>/<project>/<team>", `hint`: the first Azure board the repo names that is not that one, else any other it names, else null). `abe install check board` fails `board-unreadable` while that board is still the one in force and still refused, and `board-unwritten` while the repo Layer names no board and the record has one (the file written again without it).
  No Layer naming the board: az is `skipped` until the board is known, and the agent asks where it is, the boards `read.boards` names offered first.
- **Logins**: checked right after Read, before anything remote, on what Read found and the board in force by then (az for an Azure board: `loginsWithBoard`), az is listed `skipped` (“checked once Board picks Azure”) until the board is known to be Azure, and again once the board is Azure, against the logins service's status (`repoLogins`'s shape: needs, missing, unchecked, ready); one not ok fails `logins`, its line naming the sign-in the person runs (`! <command>` in the chat) (`abe login <tool>`, locally az's `[AZURE_CONFIG_DIR=<dir>] az login --allow-no-subscriptions`), its reason and row saying what else to know (`note`: the az folder checked, `/tmp` ones wiped on restart, what the check said; outside a checkout `abe login status` names no checkout, `outside`); az ok, its row says who it signed in as and the folder checked, so a login in another folder or tenant shows. `abe install logins` checks again. The repo using aws: each environment's aws profile is an up-front question, never the one your file on this machine gives your boxes: the profiles Read saw the repo name first (`read.awsProfiles`), then this machine's other ones (`aws configure list-profiles`, `InstallRepo.awsProfiles`), and records it per environment with `abe install env-profile`. A prod-looking profile (`prod`, `*-prod`, `abe-prod`, `prod-readonly`, an environment `prodEnvironments` names) is never offered and refused `prod-profile` when typed. Yours, in `.abe/settings.local.yaml`, names only: `logins: { gh, az }` (the accounts) and `credentials: { <env>: { awsProfile } }`; none leaves aws unchecked (`skipped`), nothing failed.
- **Sources** (superseding ADR 0027's "sources live in Claude Code local scope"): every source is the team's, an MCP server in `abe.yaml` `sources:` (`{ name, url, transport: http|sse|stdio, command?, args? }`; a literal header or env value is refused: no secret) in `abe.yaml`, written as an ordinary change. No personal MCPs. Abe's generated MCP config for every session of the repo (the install's, cards', Ask's) is the `sources:` with the same definition, so the sign-in Claude Code stored for that name and definition is reused, and teammates who pull the repo get the same set. `abe install sources --json` lists the sources Read found, each with the server Abe would add (a known system's own, `KNOWN_SOURCES[].server`: Sentry, Figma, Linear, Notion, Confluence; else the remote one the repo's config names with no header or env value), and, once, the servers in Claude Code's local scope for the main checkout that are not in `sources:` (`found: 'local-scope'`). The agent asks the person, then runs `abe install source <name>` (`--url <url> [--transport sse]` for one with no server known, or one Read never found), which adds it to `sources:`. Never `claude mcp remove`. Sign in: `abe source sign-in <source>`, run by serve itself outside any session, in the background: Claude Code's own MCP OAuth (`InstallRepo.signInMcp`, `core/src/install/source-sign-in.ts`: a headless `claude -p` in stream-json, the control request `mcp_authenticate` Claude Code does not document, the URL it answers opened in your browser and never logged, `mcp_status` polled until `connected`, 5 min; one that does not know the request says to update Claude Code), then the server's state and its probe, one reading tool call through your `claude -p` on a generated config of that one server (`InstallRepo.sourceAccount`: `ok`, `tool-error`, `timeout`, and the account it told). Every session's hook refuses Claude Code's `mcp__<server>__authenticate` tools (`signInToolRefusal`). `sources` is optional; it passes when each source found is added and reads (`abe install connection`'s probe), or is skipped. After the install, Settings › Logins & tools has a Sources group (`abe source status`: the repo's `sources:`, each server's state now, `checkItems`), each row's Sign in on ⏎ running the same sign-in and one read (`abe source sign-in`, kept by serve per source, `sources.changed` when it starts and ends; Signing in…, then Signed in · read OK or the failure).
- **Env files** (part `env-files`, rules in `core/src/install/credentials.ts`, ADR 0028): serve writes the three Abe env files, `.abe/abe.dev.env`, `.abe/abe.test.env` and `.abe/abe.prod.env` (`ABE_ENVS`, `abeEnvFile`), in the main checkout where missing, a header alone (`abeEnvHeader`, mode 600), never over one that is there, and adds `.abe/abe.*.env` (`ABE_ENV_GLOB`) to git's `info/exclude` (all of `.abe/` is). The install's session edits them directly: it trims and fills each, never asks for `DATABASE_URL` (the checks and the app get their own database); `env-map` runs in a subagent, and never prints a value. It prefills them first from the repo's own env files (`core/src/install/env-prefill.ts`): it reads them, values included, judges which feeds which environment from evidence (scripts' `dotenv -e`/`-c` and `--env-file`, README and CLAUDE.md, CI, key names, file names, in that order) and records it with `abe install env-map --file "<file> -> <dev,test,prod|not-used|not-sure>: <evidence>"`… in load order, plus `--ci <where> --ci-key <KEY>`… when environments live only in CI, kept in the record as a decision (`envFiles.mapping`, its evidence and Not sure, never a value) and written into `abe.yaml` for the team (ADR 0040, `recipeWithMap`): each placed file in `worktree.link`'s group per environment (`copy`'s when the recipe copies it; `all` for one feeding every environment), each not-used one in `env.notUsed` with its why, a not-sure one out of the groups; the evidence stays in the record and the blocks' heads. Serve then writes each file the way the repo's loader would (`abeEnvPrefill`): the files feeding it in load order, the last setting a key keeping it; a `_DEV`, `_TEST` or `_PROD` key to its own environment only; old copies (`isOldEnvCopy`), empty files and, when an aws profile is asked, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` left out; each file's part a block between `# --- from <file> · <evidence>` and `# --- end <file>`, written again on each new mapping while the person's own lines outside the blocks stay (a key they set there is left out of a block, `withAbeBlocks`); an environment no file feeds names CI's keys, when CI's evidence is for it (`ciEnvsOf`: the environments its `environment:` names, else every one). A file the session can't place is Not sure (`envFiles.notSure`, its reason), and so is one Read found with keys that neither `abe.yaml` nor the mapping places (`envFilesPlaced`, `ENV_NOT_MAPPED`), the agent asks the person where it goes and maps it again. When the repo uses aws (`asksEnvProfiles`), each environment needs its aws profile or none: `abe install env-profile <dev|test|prod> <profile|none>`, any of this machine's (`no-profile` else), written into your Layer for the checkout (`credentials`: each environment's `awsProfile`, names only). `abe run <script> [--env dev|test|prod]` (dev when none; one off for agents refused `env-off`) hands the script that environment's values (`credentialsInjection`: exactly its Abe env file's values plus its aws profile's short-lived keys from `aws configure export-credentials`, `InstallRepo.awsCredentials`; Abe's own keys, its port base and database, over them, this machine's `DATABASE_URL` for dev alone; an expired login refused `aws-login-expired` naming `abe login aws --profile <p>`); on a box only dev (`env-not-here`). A local run's checks and `abe install try` get the environment the checks part said the same way (`checksEnvOf`: `abe.yaml`'s `checksEnv`, ADR 0040, which `abe install checks-env <dev|test> --why <evidence>` writes, judged by the session from the scripts, CI and README, the person's pick over it; else an older install's `Install.checksEnv`; dev when none; `ChecksOptions.injected`; an expired login runs none, `aws-login-expired`). A card worktree gets the files of the environments on for agents linked from the main checkout, never copied, so one edit reaches every card (`worktreeCopies`, `copyAbsent`); the working copy's `abe.yaml` and `.claude/skills/` are put in over the ones the card's branch tracks, each tracked path there hidden from git (`--skip-worktree`), so the card runs on the install's pack, board and scripts and its diff never carries them. `abe install reset` deletes them. A card's or an install's session is told where they are and that it never prints, quotes or commits a value (`ABE_ENV_LINE`). The Connection check reads each added source (typed ones too) with its probe's one read (`sourceFact`: the account can't read is failed, no answer in time a warning) and each environment's credentials (`credentialsFact`, `Env file · <env>`: its aws profile, an expired login failed naming its sign-in, the account the profile is, any profile, read only through `aws sts get-caller-identity` (`InstallRepo.awsAccount`, its id alone; none said when aws can't tell), and its Abe env file's key names). Every value of the three files is redacted, whichever environment ran (`abeEnvRedacted`, `injectedSecrets`, `redactText`), from what `abe run` hands back, from each check's output and `checks.md`, and from the session's shipped logs (`abeEnvValues`, each known to the session's redaction as `ABE_CREDENTIAL_<ENV>_<KEY>`, never in its environment). A session in that checkout gets every tool of each source's own MCP server allowed, writes too (`mcp__<source>__*`: `accessRules`, `core/src/install/agent-envs.ts`; never a token in a file; no per-tool deny, no wildcard in the server's place, which Claude Code skips) and one line in its instructions naming its sources (`sourcesLine`). It reaches only the environments on for agents (ADR 0029): your `agents.dev`, `agents.test`, `agents.prod` for this repo (dev and test on, prod off; yours alone, in `.abe/settings.local.yaml`: `abe settings set agents.prod true --mine`, Settings › Agents › Environments, prod's toggle with its warning; the repo's file, an Override there included, never turns one on, and a Layer's `reach` write name for prod is refused `prod-off`). The install's own session runs with no sandbox, like your own Claude Code. Every other session's sandbox is about secrets and files, not the internet: a local session's commands run under Abe's own Seatbelt profile (`core/src/session/seatbelt.ts`: `jailed`, `seatbeltProfile`, written by the tmux runner as the session's `jail.sb` and `jail.sh`, named by `CLAUDE_CODE_SHELL_PREFIX`; Claude Code's own sandbox off, `Bash` allowed, credentials scrubbed by `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`): any host outbound, raw TCP and ssh too; writes only in the worktree, its writers', the package caches and its temp folder; none of the person's secrets read (`HOME_SECRETS`, the checkout's az folder; the same paths as file-tool deny rules), no Keychain service, no Unix socket but its own. A box session's commands run in bubblewrap the same way (`boxJailScript`, `BOX_JAIL`, written as root beside the managed settings: the network shared, `BOX_HIDDEN` hidden, its own pid namespace, the login unset; no `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`, whose own bubblewrap around each command forbids the jail's user namespace). One on is reached in full, read and write: its Abe env file read. One off is not reached at all, by no parsing of commands: its Abe env file is not linked into a card worktree and is denied to the session's file tools and jail in the main checkout and the worktree (the install's own session excepted: it writes all three), and so are the repo env files that feed only environments off or that are not placed yet (`offRepoEnvFiles`, the install's mapping) and every other known checkout's Abe env files (`yourCheckouts`); its aws profile's keys are never handed on (no session reads `~/.aws`); its hosts stay reachable but take nothing without a key; and a check or `abe run --env <it>` is refused `env-off` (`envNotEnabled`). The session is told which it reaches (`agentEnvsLine`); a change applies to the next session, and each live session launched on others is typed a note to finish its turn and write a handoff (`Sessions.envsChanged`, on every `settings.changed`). Commands that print a credential are denied in every session (`SECRET_OUTPUT_DENY`).
- **The live read** (`install-connection.ts`), inside the logins, board and sources checks: `abe install connection` has serve read live and show facts, each ok, failed (why, fix) or skipped: the board (Azure Boards' org, project, team, current iteration and its 3 newest cards; GitHub Issues' repo and its 3 newest cards), GitHub (origin's repo, never its URL; the account gh acts as; whether it reads pull requests; when that account can't, each other signed-in gh login is tried read-only on its own token, gh's active login never switched, and the first that reads it is set as this repo's `logins.gh` in `.abe/settings.local.yaml`, as `--mine` does, the row saying so; none: every login tried is said, with `gh auth login --web` as one that can), the cloud (cards in cloud boxes: the settings' `box.profile`, an `abe-*` one, and `box.region`, and the profile's account from `aws sts get-caller-identity`; missing: `set up by the platform Terraform (infra/aws)`; cards on this machine, when the repo uses aws: where, the profile `logins:` names, else the checkout's `box.profile`, else the one the person picked at Logins (Logins checks aws on it too), the aws login as Logins checked it (skipped: `not checked`, not failed), the account only for an `abe-*` profile), each added source (its MCP server as `claude mcp get` says for the person; connected, the account it is signed in as, `Account`, `Org`, `Project` as far as it told: `install-source-account.ts`, one `claude -p` of the person's, on Haiku (else Sonnet, else the first `allowedModels` allows: `sourceAccountModel`), with only that server from your `~/.claude.json` (a repo's `.mcp.json` never: a server only there is `none`, as it never loads in a session), all its tools allowed (Abe blocks no MCP call), no built-in tools, two turns, 60 s; nothing told, failed or late: the MCP status alone). The agent shows the person what was read and fixes what it can; a warning the person accepts stays a warning. A source skipped is taken out of `sources:`, the rest of the file kept, so no session reads it.
- The hint order: logins, board, sources, env-files, worktree, checks, workflows, skills, verify, prototype, done. The agent may change it: checks and skills need no running app, so they never wait on the gate; the Verification pack starts once the app runs.

- **Resume**: `abe install` (`:install`) on an install not Done reopens the same Claude Code conversation (`session reopen`); on a Done one it starts a new conversation seeded from the parts record. - **The session**: the install runs in the repo's Abe chat (kind `abe`) in the main checkout itself, following the `install` skill (`/abe:install`); `abe install` opens it, or reopens it (Resume, above).
