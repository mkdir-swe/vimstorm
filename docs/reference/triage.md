# Triage and Improve

`abe triage` (which cards are ready, which need info) and `abe improve` (changing Abe for yourself).

## Triage

Rules in `core/src/triage/triage.ts`, handlers in `serve/src/triage/triage.ts`, core's skill in `core/skills/triage/SKILL.md` (upstream's triage, cut to four verdicts), kept in `<state>/triage/` (`last.json`, `unreadable-<time>-<random>.txt`).

- `abe triage [--team] [--repo <owner/repo>]` reads your cards in the team's current sprint (`Board.currentSprint`; none is `no-sprint`), or with `--team` the team's whole backlog, leaves out the running ones (a session not ended, a Factory run not done: `skipped`), adds the open issues of `--repo`, else of the checkout's `origin` on GitHub (`Tracking.issueList`), but no spec issue or slice of a Factory run still going or merged (`specIssuesOf`: its card's work, closed by its pull request's merge; a run done unmerged leaves them to triage), and asks one one-shot as a reader with the skill. The answer is one verdict per item: `ready`, `needs-info` (with its one question), `too-big` or `not-for-agent`, each with its reason; anything else (no JSON, a missing or unknown id, needs-info without a question) is refused `triage-unreadable`, its raw text kept. It writes nothing on the board; it keeps the verdicts as the last triage and emits `triage.done` with the counts.
- `abe triage apply <id…>` acts on the last triage's needs-info cards only (`WRITES`): one comment (upstream's AI disclaimer, why, the question) and the `needs-info` tag; a triage comment already asking that question is not written again. Every other id is refused on its own line (`not-triaged`, `not-a-card` for an issue, `not-needs-info`).
- `abe triage launch <id…>` runs `abe factory run` in the triage's checkout for each of its ready cards, each placed as any launch is (`placeCard`, below): in your environment a card is `queued` once your running and starting boxes reach `limits.maxBoxesPerPerson` (the repo's cap: yours only lowers it with a plain entry, raising it takes an Override with its reason; a stopped box never counts), held in the launches' queue until a box stops or is deleted, or the limit rises; on this machine (`serve.target: local`) a run holds no box and always starts. A card that runs already (`running`, even when its run waits on you with its session ended), a refused run, an issue or a card that is not ready is `refused`, each id on its own line. The last triage is one per `serve`: a triage in another checkout replaces it.
- An answered card: a card tagged needs-info, or one the last triage called needs-info, has its comments read (`Board.show`) from triage's own question on; the prompt carries them as `### Since triage asked`, and the skill reads an answer there and a card still tagged needs-info as waiting on it. The Abe chat's `/abe:triage` runs them.
- Ports `Board`, `Tracking`, `OneShot`. Event `triage.done`.
- Tests: rule tables in `core/src/triage/triage.test.ts`; the CLI seam (the fake Azure DevOps, a fake `gh`, the fake `claude`, a real `tmux` for launched runs) in `serve/src/triage/triage.test.ts`.

## Improve

Rules in `core/src/improve/improve.ts` and `core/src/improve/personal-commands.ts`, handlers in `serve/src/improve/improve.ts`, core's skill in `core/skills/improve/SKILL.md`, kept in `<state>/improve/` (`proposals/<id>.json`, `undo.json`, `suggested.json`, `unreadable-*.txt`).

- **The personal Layer** is your Abe config folder (`$ABE_CONFIG_DIR`, else `~/.config/abe`): `settings.yaml`, `keys.json` (a key → its action or actions), `commands.yaml` (personal commands), `skills/<name>/SKILL.md`, and `nvim/…` (your Neovim config, a developer's only: loaded over VimStorm's under the Feels `vimstorm` and `vim`, last, by `nvim/lua/config/userconfig.lua`; an error in it is a balloon). Paths are relative to it; anything else (absolute, `~`, `..`, hidden files, a link out of the folder) is `outside-personal-layer`.
- `abe improve <wish…>` asks one one-shot as a writer (Opus under `allowedModels`) with the skill, the settings keys, the personal commands' format, the view components and your Layer's files as they are. It answers `{kind: change, summary, files: [{path, after}]}` (after null deletes), `needs-code` or `nothing`. A change becomes a proposal `{id, wish, files: [{path, before, after}], summary}`, nothing written; a keys, commands or settings file that does not read (settings merged with the Layers above, so lowering a value still takes an Override) is `invalid-proposal`. A code wish (Send to Abe) answers a draft issue for `improve.issueRepo` (default `mkdir-swe/vimstorm`), filed by nothing: the Abe chat shows it and runs `abe issue create` once the person says so. Its text output is a block to paste as it is (`**Fix here** · your own files: <summary>` and each file's lines, or `**Send to Abe** ·` the draft's title and whole body), then a `Next (for you, not to show):` line; `/abe:improve` pastes the block before it asks. Retro makes its personal proposals with `makePersonalProposal(ctx, {wish, summary, files, from, model})`.
- `abe improve apply <id>` writes it when every file is still as proposed (else `stale-proposal`; once only, `already-applied`), keeps the state before, and emits `settings.changed` with `files`. `abe improve undo` puts the last applied state back exactly (contents and deletions); each undo goes one further back, up to 20. A file changed since that apply is `stale-undo` unless `--force`.
- `abe improve suggest`: only with `improve.suggest` on in your own Layer (`suggest-off`; no other Layer may set it), at most once in 24 hours (`suggested-today`); the one-shot sees your Layer and the commands run lately, and a suggestion is a proposal or nothing (never an issue).
- **Personal commands** (`commands.yaml`): `word: [noun, verb…]` or `word: { argv: […], summary: … }`. `abe help --json` lists them as `personal` (Command mode reads it); `abe <word> [more…]` runs `abe <argv…> [more…]`. A word of the table is never yours, and the argv starts with a command of the table.
- **View tweaks** (`core/src/improve/views.ts`, `ui/src/shell/views.ts`): the personal setting `views: [{screen, node, hide: true | order: <n> | label: <words>}]`, one change each, applied in order. Each screen's node ids are core's `VIEW_NODES` (the Factory view's `board`, `board-head`, `col:<state>`, `chat` and the parts of a Sheet; status's `serve`, `sessions`, `reload`); a `views` value with a tweak naming another is dropped from the merge whole with `unknown-node` (so `settings set` and Improve's proposal refuse it), one labelling a wordless part with `invalid-setting`. Every screen the bridge opens is wrapped in `withViews`: it reads `settings get views` on open and on every `settings.changed`, and `applyViews` hides (its Stack size too), reorders and relabels (a column's name, a header's title, a row's text) the tree before it is sent; the screen gets the tweaks too (a `views` input) and walks the Board's columns `arranged` as drawn, so its keys never land on a hidden one.
- Ports `OneShot`, `Tracking` (the issue, an open pull request), `LayerPulls`. Event `settings.changed` (with `files`) on apply and undo.
- Tests: rule tables in `core/src/improve/improve.test.ts` and `core/src/improve/views.test.ts`; the CLI seam (the fake `claude`, a fake `gh` for the issue, a temporary personal Layer) in `serve/src/improve/improve.test.ts`; `LayerPulls` against a fake `gh` in `ports/src/github/layer-pulls.test.ts`; the tweaks over the overview `ui/src/shell/views.test.ts`; `:improve` and `:improve undo` in Command mode `ui/src/chat/improve-chat.test.ts`; a tweak or a proposal naming no node refused through the CLI `serve/src/improve/improve-ui.test.ts`.
