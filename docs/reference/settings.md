# Settings and logins

The Layers, where each setting is read from, Overrides, hook points, the Settings dialog's catalogue, and the logins Abe checks and stores.

## Settings

Layers core → feel → repo → individual (yours) (ADRs 0010, 0011, 0030; `feel` is the Feel's bundle over core's defaults, its own step in `explain` and `list`: `from Feel VS Code`). Settings are read from three files (`PLACES`, `layerOfPlace`): the repo's `abe.yaml` (committed when the install is Connected, in Abe's `info/exclude` block when Local only), yours on this machine `~/.config/abe/settings.yaml` (`$ABE_CONFIG_DIR`) and yours for this repo `.abe/settings.local.yaml` in the main checkout (always in Abe's `info/exclude` block; every worktree of the repo reads the main checkout's). A key's `places` says which it is read from: an editor preference or your environment (`ui.*`, the Feel's switches, keys, tree, tabs, chat, `role`, `views`, `localMode`, `improve.*`, `box.region`, `box.owner`, `stores.*`) only from yours on this machine; `box.profile` from either of yours, this repo's winning; `serve.target` (where the repo's cards run, 3.2.2) from all three, applied yours on this machine, then the repo's file, then yours for this repo (the repo decides, yours for this repo over it, yours on this machine where neither says; a plain `abe settings set serve.target` writes yours for this repo in a checkout, else yours on this machine; `--repo` the repo's); a factory or agent setting (no `places`: `board` (its `board.area`, one area path or a list, `board.tag`, `board.excludeLanes`, one swimlane or a list, and `board.notTag` set, read, explained (each its own value and what it is, `boardFieldExplain`) and unset as keys of their own, `BOARD_FIELDS`; `board.provider: github`'s repo is `board.repo`, else the checkout's origin, filled into the snapshot with `logins.gh` as `board.githubAccount`, `githubBoardFilled`), `checks`, `sources`, `reach`, `environments`, `limits.*`, `models.*`, `autoMerge`, `factory.done`, …) from the repo's file and yours for this repo, yours over the repo's, never from your file on this machine; yours for this repo alone (`logins.gh`, `logins.az`, `githubIdentity`, `credentials`, `testWrites`, `agents.*`, `board.azureConfigDir`) only from `settings.local.yaml`, the repo's entry refused saying why (`onlyWhy`). `core/src/layer/settings`: the keys (`SETTINGS`: schema, core's default, how a plain entry adds, which changes need an Override, `places`), `mergeSettings(sources)`, the files' layout (`places.ts`), the Override rule (`readOverride`, `overrideReason`, `loweredText`) and Reach's `isWriteName`. Commands: `abe settings get <key>` (the merged value), `explain <key>` (what the key is, `about`, then each Layer's value, the winner, any Override), `set <key> <value> [--repo | --mine] [--override --reason …]` (`--repo` the repo's file, `--mine` yours for this repo, `--here` an alias of `--mine`; with neither, an editor or environment key goes to your file on this machine and a factory key to `--mine`; lowering an upper value takes an Override with its reason; it says what it wrote, then `in force: <value> (from <layer>)` where that differs; a plain list entry of a key that only adds which adds nothing over the Layers above, the one below left out, is refused `override-required`, as a drop is; the file is written back with its other lines byte for byte, flow maps and lists as written (`yamlText` splices only the changed entries; every settings file write shares it)), `unset <key> --repo|--mine` (takes the entry out), `check <dir|file>` (a repo's settings files; exit 1 on any problem). A handler reads the settings in force with `ctx.settings.at(ctx.cwd)` (`SettingsService`, `serve/src/settings/snapshot.ts`): `.values` is typed, `.explain(key)` says where a value comes from, and the checkout's files are watched from then on (`settings.changed`). serve keeps one merged snapshot per checkout: its first lookup reads the files, later ones read none, and the poll (every 500 ms) makes it again when one of its files changed; a write of serve's own polls at once. `ctx.settings.facts(dir)` is what serve derives from it there, so every command agrees: your gh login, az folder, box profile, the environments agents reach and the checkout in local mode. A file's Overrides sit under `overrides: { <key>: { value, reason } }`. The layer files are read with `ports/src/mac/settings.ts` directly (no port interface): tests use real temporary folders.

**Overrides** (ADR 0010 amended 24 Oct 2026): every setting can be overridden personally, with intent and visibility. A change of yours that loosens a value above (auto merge on, a check cut, a model or a bigger box allowed, an idle box kept longer) is an Override in yours: `abe settings set <key> <value> --override --reason <why>`; without `--reason` it is refused `reason-required`, naming the key and the command. The file keeps `{ value, reason, since }` (`since` the ISO time `set` or `propose` wrote it; `readOverride`, `loweredText`: `overridden by individual: <reason> · since <date>`). It shows in `settings explain` / `list`, as an info row on Problems (`kind: override`, `code: personal-override`, never counted or landed on, its fix strip the proposal to the repo), on a Factory run launched under it (`Run.personal` / `FactoryRunData.personal` from `runOverridesIn` at `factory run`: the Chat header's `pill` `Override · autoMerge on`, its tooltip why and since when, and the story dialog's Session row); `abe settings propose <key> <value>` (a pull request on the repo's `abe.yaml`) is suggested in `set` / `explain` / Problems, never required (`core/src/layer/settings/personal.ts`). Reach's write names are granted only by an Override in the repo's file (credentials, not settings): yours granting one is refused. Yours follows you to your boxes: each cloud launch hands yours in force at the checkout to the box (`abe session run --layer <JSON>`, `handedLayer`: this machine's paths left out), which makes it the box's own from then on (`boxLayer`: an earlier launch's entries gone), so the run, its pull request's auto merge included, follows what `settings explain` shows locally.

**Hook points** (ADR 0035, `core/src/repo-hooks/`): `hooks:` in the repo's `abe.yaml` (the team's alone) maps each role Abe calls to its place: the scripts `start`, `stop`, `seed`, `db`, `query`, `prototype-start`, `prototype-stop`, `worktree-setup`, the skills `run-app`, `testing`, `verify`, the headings `find-out` and `read-data`. A role left out is today's place (`DEFAULT_HOOKS`; `worktree-setup` none). Abe asks the module for a role (`repoHooksIn` of a checkout's settings), never a path. What an agent's `abe run` may run (`runScriptIn`, the same rule on a Mac and a box) comes from the main checkout's committed `abe.yaml` (`committedHooks`, `git show HEAD:abe.yaml`), handed to a box with its sync (`SessionSync.hooks`, kept beside the box's workspaces), never from the clone. A sync carries the hook scripts' folders with the team's files (`syncTeamPaths`). Settings › Factory policy › Hook points shows each role as a text row.

The Settings dialog's catalogue: `core/src/layer/settings/pages.ts` is the tree (`SETTINGS_TREE`, Problems first while there are any, groups that open their first child) and each page's rows (`PAGES`: key or `key#field`, label, control kind, help, group caption, choices with their `words` (what a control and a source line say, `afterDelay` is `after a pause`) and `none` (what no value means, `no limit`), `personalOnly`, `fixed` lines with no setting, `link` for a line naming a home row on another page: its value, ⏎ goes there); every key has its home rows on exactly one page (`NO_ROW`: `chat.width`, the drag of the column's edge), and a page with nothing in it is out of the tree. VimStorm's look and Abe's agent defaults are keys too: `ui.theme`, `ui.density`, `ui.font.*`, `chat.openByDefault`, `chat.width`, `models.coordinator|reader|writer`, `effort`, `subagents.max` (the Subagents limit a launch tells the session, `withSubagentsMax`). The **Feel** (`settings/feel.ts`): `ui.feel` (`vimstorm` | `webstorm` | `vscode` | `vim`, yours alone; `vim`: VimStorm's switches with stock Vim keys, your `~/.config/nvim` loaded on top, `nvim/lua/config/feel_keys.lua`) picks a bundle of switches (never the theme: dark or light is Appearance › Theme's alone) `tree.autoReveal`, `tree.singleClick`, `tree.decorations`, `tree.compactFolders`, `tabs.limit`, `tabs.dirtyDot`, `tabs.preview`, `files.autoSave` and Vim mode `editor.vim` (off under `webstorm` and `vscode`; `nvim/lua/config/vimmode.lua` keeps the editor typing): `mergeSettings` walks `ui.feel` first and starts each of those keys from its Feel's value instead of core's default, so any Layer that writes one wins (and a Feel's value lists and explains as `from Feel <feel>`, its own Layer `feel`). `abe settings feel` gives them grouped (`FeelSwitches`); the bridge sends that as the `feel` shell effect once serve answers, on `project` and on `settings.changed` (whole-state), and the app keeps it as its `Feel` global (`app/src/factory/feel.rs`). **Imported config** (`core/src/import`): pure mappers from another editor's files to rows (`ImportRow`: the source's words, the setting it becomes or `no match here`, ticked): `vscode.ts` (`settings.json` / `keybindings.json` as JSON with comments, `jsonc.ts`; the theme to the nearest built-in), `jetbrains.ts` (the newest WebStorm config folder's `editor-font.xml`, `colors.scheme.xml`, the one-to-one options of `ui.lnf.xml` (tab limit, preview tab, modified mark, UI density, UI font), `ide.general.xml` (autosave) and `projectView.xml` (select opened file, single click, compact directories), the active keymap), `vim.ts` (`~/.vimrc`, `~/.config/nvim/init.{vim,lua}`: `guifont`, `autowriteall` and its `no` / `false`, every one-line `colorscheme` form, `background`; each option of a `set` its own row, comments left out; the leader, options and mappings listed only); each picks its Feel first. Keys go onto the **Keymap catalogue** (the part import needs: `core/src/theme/keymap.ts`, `KEYMAP_ACTIONS`: each action is one of VimStorm's own keys, `nvim` its map's lhs; `import/keys.ts` VS Code command ids, JetBrains action ids and Vim right-hand sides onto it): a binding on an action is ticked as `<key> = <action>` (`ImportRow.bind`, the key as macOS writes it, `⇧⌘P`); a two-key chord, a removal (`-command`), a command VimStorm has none of, a key that types (`bindable`: only ⌃ / ⌘ keys, F-keys and ⌥ with a named key reach nvim as keys), a key VimStorm's window keeps or swallows (`WINDOW_KEYS`, checked against `app/src/input/keymap.rs`' Window, App and Ignored rows) and Vim's leader / plain-key mappings stay `no match here` with why; a key that is another action's VimStorm key says `covers ⌘K Commit`, a Vim mapping of one mode says every mode binds it here. `abe settings import vscode|webstorm|vim [--dry-run] [--only k,k]` (`serve/src/layer/settings-import.ts`) reads only those paths under HOME and writes the ticked rows to your file on this machine as plain entries (the later of two rows for one setting wins) and the ticked key bindings into your Layer's `keys.json` (a key → its action, the keys there kept; `--only key:⌘Y` names a binding, a comma after a modifier being the key's own; a keys.json that is no JSON object refuses `bad-keys-file`, nothing written); a row the merge refuses is named, not written. `abe settings feel` carries your keys.json's bindings as `keys` (`keyBinds`: each key's nvim names, the US and the Swedish layout's, and its action's VimStorm key), the theme watch reads keys.json too so a change resends the Feel, and nvim binds them over any Feel's keys (`nvim/lua/config/keys.lua`: each does what its action's VimStorm key's map did, in Normal, Insert and Visual mode, while the editor has the keyboard: a native surface does not forward them yet). A row the picked Feel already gives is not ticked (`feelRows`: unless `--only` names it or something else is in force there), so a later Feel switch moves it. A source whose config is not there or does not read (`unreadableSource`: VS Code's `settings.json` missing, not JSON (with its line and column) or no object; no JetBrains IDE folder; none of Vim's files) is refused `import-unreadable`, nothing written, unless `--only` names what to take. `abe settings list` (`settings/list.ts`) gives every row's value in effect, its source (`built-in`, `from Feel <feel>`, `Repo`, `Yours`, `fixed`), `differs` when yours differs from the Layers above (`Merged.without('individual')`), greyed choices with why and `prs`, every open pull request proposing the row on the repo's file (`withProposals`, found by its branch through `LayerPulls.open`); its scope names the checkout's repo as GitHub does (`acme/shop`, from origin), never its folder; `--files-only` (both `settings list` and `settings problems`) answers from the settings in force alone, at once: no open proposals, no gh accounts, no login, tool or Docker check; `abe settings problems` (`settings/problems.ts`) lists logins (one whose tool cannot run is `unchecked`, never `expired`), tools, the setup (`settings/setup-problems.ts`: no board for the repo, `serve.target: cloud` with no AWS profile or region; not on a box), Overrides without a reason, settings files that do not read and dropped settings, worst first, each with a `fix` command or the row to `open`; `settings/search.ts` is the dialog's `/` matcher over any corpora of `SearchItem`s. `abe tools check` (`core/src/install/tools.ts`, `serve/src/install/tools.ts`) runs each tool's check through the `ToolProbe` port (`ports/src/claude-code/tool-probe.ts`: serve's own PATH; `fakeToolProbe` in tests); node's row names where it is and the version manager it is under (`22.11.0 · Volta`), and a missing or old node's fix is that manager's install (the first found locally, else `brew`). claude's row checks every `claude` on PATH (`ToolProbe.runEach`) against `CLAUDE_MIN` (2.1.300: an older Claude Code rejects a session's hook events with a Settings Error dialog): an old one first on PATH is flagged naming the one sessions use, its fix its own `update`. `abe settings propose <key>[#<field>] <value> --reason …` (`settings/propose.ts`, `serve/src/layer/settings.ts`) proposes one setting to the repo as one pull request through `LayerPulls` (the Git Data API over the default branch's file, the checkout never touched): `abe.yaml` in the checkout's GitHub repo (`proposalPath`), on the branch `settings/repo/<key>` (`proposalBranch`; `<key>.<field>` for a field row), the reason the body's first line, an Override with that reason where a plain entry may not lower the value above; a second proposal of the same setting (its open pull request found with `Tracking.prFind`) moves the branch and updates that pull request; the value is checked on the files here before GitHub is asked, and again on GitHub's; the repo is named by its GitHub name (`Repo acme/shop: …`); a wait over 2 s says it waits on GitHub (the command's `waits`); `settings list` waits at most 5 s on GitHub for the open ones, else lists without them. An editor preference, your environment or a key yours alone is refused `personal-only` (`yours alone: not for the repo`).

## Logins

A person's GitHub, Claude Code and `az` logins live in one secret of theirs in the tooling account (ADR 0016; the org Terraform's `terraform/logins`, people in the org Layer's `teams/<team>/people.yaml`), one JSON document holding each tool's login files (paths under `HOME`, base64). Rules in `core/src/logins/logins.ts`, the service in `serve/src/logins/logins.ts`, IO in `ports/src/aws/login-store.ts`.

- `$ABE_LOGINS_SECRET` names the secret (the box's service sets it from the root's `secrets` output; locally it is unset, so nothing is restored over the local machine's own logins). `$ABE_LOGINS_STORE=file://<dir>` puts a folder in Secrets Manager's place; `$ABE_LOGINS_EVERY_MS` shortens the look for refreshes (default 20 s).
- On start `serve` restores each stored login where its tool reads it (`~/.config/gh/hosts.yml`, `~/.claude/.credentials.json`, `~/.azure/{azureProfile.json,msal_token_cache.json,clouds.config}`, 0600), dated when it was stored; a login newer here is kept and stored. A tool with nothing stored comes from its seed, the secret's sibling (`abe/<person>/github-token` through `gh auth login --with-token`, `abe/<person>/claude-token` as Claude Code's credentials file), then is stored. Every look (20 s) it writes back a login whose files changed, only that tool's entry, read-modify-write; every 15th it compares every login with the stored ones, the newer winning (another box's newer one is pulled here, never overwritten). Until a restore has worked nothing is written back; each look tries the restore again. Only a tool's own files are ever restored.
- A box's sessions (`Logins`) get their `CLAUDE_CODE_OAUTH_TOKEN` and GitHub token from the restored files once `$ABE_LOGINS_SECRET` is set; without it they read the seeds directly (`$ABE_OWNER`).
- `abe login github|claude|az` runs the tool's own device or browser login on this terminal (`gh auth login --web`, `claude setup-token` under `script` so its token is read off the screen, `az login --use-device-code`), then `serve` stores what it wrote; the value never crosses the socket. Refused where no secret is named, except `abe login az [--tenant <id>]` locally: Entra's security defaults refuse a box's device code (`AADSTS530035`), so there `az login` runs in the browser into a private folder of its own (`AZURE_CONFIG_DIR`, never `~/.azure`, removed after) and its files go straight into your logins secret (found by its `abe:owner` tag on your SSO, as browser profiles are) for your boxes to restore (`abe --on <box> login restore` for a running one). A local machine with no boxes (no `box.profile` or `$ABE_BOX_PROFILE`, or one its aws config lacks: `macBoxes`, read from files, no aws run) never reaches aws or a logins secret: `abe login az` signs in in the az folder in force there (else az's own), `abe login aws --profile <p>` runs SSO's login alone, and each says `not stored: this machine has no boxes (<why>)`. Locally `abe login github|claude` is the tool's own browser login (`gh auth login --web`, `claude auth login`, `MAC_LOGIN_ARGV`), never stored: a box signs in on its own. An Entra refusal (`AADSTS530035`, `53000`–`53004`) in a login, `abe login status` (`blocked`) or a board's token read is named with what to do.
- `abe login status` says `ok`, `expired`, `missing` or `unchecked` per tool (`gh auth status`, `az account get-access-token --resource <Azure DevOps>` (the board's own token, so a login with no subscription passes; only its end printed) in the az folder in force at the checkout, Claude Code's credentials file's end; `unchecked` with why: the tool not on serve's PATH, a `claude auth status` failing on something else), each not ok with its way out: locally (no login secret) the tool's own login (`gh auth login --web`, `claude auth login`, `az login --allow-no-subscriptions`, `AZURE_CONFIG_DIR=<dir>` in front when `board.azureConfigDir` or serve's `$AZURE_CONFIG_DIR` is in force), on a box `abe login <tool>`; az's row names the folder it checked (a `/tmp` one: wiped on restart, use one under `~/.config`) and the check's first stderr line when short and holding no token (`said`); one an Entra refusal blocks (`blocked`: `AADSTS530035` security defaults, the box's case, → `abe login az` locally; `53000`–`53003` Conditional Access → an admin; `53004` → set up MFA) says that instead, with no fix to run; `abe login restore` does the start's restore again.
- `aws` is a stored login like the others (`.aws/config` and SSO's `.aws/sso/cache/*.json`): `abe login aws --profile <p>` locally runs `aws sso login --profile <p>` in your own `~/.aws` and stores only that profile's `[profile]` and `[sso-session]` (added to the stored config, never `[default]`) and only that profile's own SSO token (the cache file named by the SHA-1 of its `sso_session`, or of a legacy profile's `sso_start_url`; another session's token never leaves the local machine, and a profile it can't pin to one file is refused, nothing stored) in your secret for your boxes; on a box the restored login lives in a HOME of aws's own, `~/.abe/logins/aws` (`AWS_LOGIN_HOME`: its `.aws/config` and `.aws/sso/cache/`), apart from the `~/.aws/config` Reach writes for box sessions, which it never overwrites; there `abe login aws --profile <p>` runs `aws sso login --use-device-code` with that HOME. Only Abe's own check and sign-in, and an install's local start (`awsLoginEnv` in `ports/src/aws/login-store.ts`), run aws on it; a session's env never points at it and the managed deny rules (`CONTAINER_SECRETS`) keep agents from its files. Its check is `aws sts get-caller-identity --profile <p>` (who: the role session's name), run only for a profile a repo names.
- `logins:` (the repo Layer, `core/src/logins/logins.ts`) lists the logins a repo needs: `gh`, `claude`, `az: { tenant }`, `aws: { profile, sso }`; a lower Layer adds a tool or replaces its options. `abe login status --repo <checkout>` (also from a session) adds `repo`: each need's state, who and sign-in, `missing`, `unchecked`, `ready`. serve's `repoLoginStatus(ctx, repo)` (`serve/src/logins/logins.ts`) is the one answer to "which logins does this repo need and which are missing"; a Factory run's launch (local or on a box) puts the run at Needs you with `repoLoginsReason` when any is not ok, so a teammate's first card asks for them. A repo with no `logins:` runs no check.
- No value goes into an event, a reply, an error or argv (`put-secret-value` reads `file:///dev/stdin`).
