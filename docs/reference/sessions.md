# Sessions

Claude Code sessions owned by `abe serve`: launch, state, Chat's data, hooks, one-shots and Ask.

## Sessions

ADR 0020. `abe session launch --card <id> --repo <path>` reads the card from the Board, makes (or reuses) a worktree on `card/<id>-<slug>` beside the checkout (`<repo>-wt/<id>-<slug>`; a new branch starts from origin's default branch fetched then (`git fetch` asking `gh` for the login, never a prompt, at most 8 s: `FETCH_TIMEOUT_MS`), never the checkout's `HEAD`, with no upstream: `BRANCH_BASE_REFS`; origin not reached is origin's as last fetched, no origin the checkout's own `main`, each with its note; the session's `base` in `meta.json` and `session show` says which, `base        origin/main at 1a2b3c4, fetched at launch`), and starts `claude --settings <file> --plugin-dir <plugins>/<id> --session-id <uuid> --append-system-prompt <core's instructions> <launch prompt>` through the `SessionRunner` port (`core/src/ports/ports.ts`). Local is `ports/src/mac/tmux.ts`: a `tmux` server of `serve`'s own (`<state>/tmux.sock`, `-f /dev/null`, never your default server), `claude` started by `env -i` from a variables file the pane removes once read, so its environment is exactly `sessionEnv`'s (`core/src/session/session.ts`): `HOME`, `USER` (Claude Code finds its Keychain login by it), `PATH` with `<state>/bin` (the session's `abe`) first, then serve's own (the local serve reads its person's login shell's PATH once at start, `$SHELL -lic` with a 2 s budget, and puts it before the PATH it was started with and the node managers' folders found on disk, Volta, nvm, fnm, asdf, mise, `core/src/install/serve-path.ts` / `ports/src/mac/serve-path.ts`; `$ABE_LOGIN_PATH=off` keeps the PATH it was started with), `TERM`, the locale, `serve`'s `DATABASE_URL` (a local workspace's database; a box's workspace has its own), its `ABE_SOCKET` and `sessionReach(ctx, 'local')`'s read names. A new local card session (not one moved back or resumed) whose repo needs node (a `package.json` at its top unless a `bun.lock` is there, or a `setup` running npm / npx / pnpm / yarn) and on whose PATH no node runs (`node --version`: a manager's shim with no node set counts as none) is refused before anything starts (`no-node`, with the manager's install as the fix: `nodeAtLaunch`). The `claude` a local session runs is the first on its PATH at least `CLAUDE_MIN` (`claudeForSession`, each one's `--version` kept until its file changes); none is refused `old-claude`, naming the version, where it is and the fix. Its settings turn Claude Code's own attribution off (`attribution: { commit: '', pr: '' }`): commits and pull requests follow the repo's style. A box's runner (the workspace container on the session's box) replaces the adapter, not the rules. Sessions outlive `serve`: `abe serve stop` leaves `tmux` running, and the next `serve` reads `<state>/sessions/*/meta.json` back and listens on the running ones' sockets.

- **Hooks.** The settings register `abe hook <event>` for every event in `HOOK_EVENTS` (all of Claude Code's but `WorktreeCreate` / `WorktreeRemove`). The hook client (`hooks/src/hook.ts`) sends `abe hook <event> --payload <json>` to `$ABE_SOCKET`; `serve` parses its payload once, appends it to `<state>/sessions/<id>/hooks.jsonl` and steps the session by core's `sessionStep` (`core/src/session-state`: `(meta, input) → { meta, events }`, the input a hook with the cards serve made of it, an Esc read from the transcript, a dialog gone, or a card change), keeping `meta.json` once per input; the state moves: waiting after `Stop` (unless a subagent still runs, started within the hour and not stopped: a background writer, whose end wakes the coordinator, so its `Stop` stays working and its idle notice changes nothing), `StopFailure`, `PermissionRequest`, `Elicitation` and the asking `Notification`s, ended after `SessionEnd` (not `/clear` / `/resume`), unchanged for events that fire while idle, working for anything else. A waiting session's `waitingOn` (`core/src/session/waits-on.ts`) says on what: its `turn` (idle, your turn: `idle since 18:04` in `session list`, `○ Idle` on every screen, never counted), a `question` card open in Chat, or a `dialog` in its terminal; only the last two need you (`waitsOnYou`). A Factory run's session that ends its turn with no step done and no `needs-you` still puts its run at Needs you (`waiting on you in Chat`: nothing else moves it on); a prototype's run never does. Each change is a `session.state` event, `waitingOn` with it. The state never comes from the screen, and from the transcript only when no hook comes: Esc mid-turn runs none, so its `[Request interrupted by user…]` line (core's `interruptedAt`, read as serve follows the transcript, never one read in after a restart) moves a session working since before it to waiting (cause `interrupted`, unless a subagent runs) and its Factory run to Needs you (`INTERRUPTED_REASON`), your next message clearing it; the transcript path and the last assistant message come from the payloads (`transcript_path`, `Stop`'s `last_assistant_message`). A session keeps every running subagent run and the newest `SUBAGENT_RUNS_KEPT` (30) ended ones, so a long Factory run's `meta.json` stays small. The hook client gives up one second after it started (`HOOK_DEADLINE_MS`; a PermissionRequest, an answered PreToolUse and a UserPromptSubmit wait longer): serve's own waits for a hook (Chat's transcript read on, an Elicitation's paste on its way in) end within `HOOK_WAIT_MS` (half of it), and a hook answered after its client gave up anyway (serve busy) is logged in `serve.log`, never dropped silently. A session whose `claude` is gone without a `SessionEnd` is ended on the next look. A `claude` that runs no hook within `SESSION_START_TIMEOUT_MS` (a minute) of its launch (a settings error dialog, an old `claude` first on `PATH`) is stopped and ended with `reason` `noStartReason(screen)` (`NO_START` and what its terminal showed, read just before the stop: the dialog's lines; until its first hook the session is `starting`, not `working`, and a message sent meanwhile is queued) (`startOverdue`, looked at every 5 s and before `session list` / `show` / `factory status` answer): a `session.state` event with cause `no-start` and the reason, and its Factory run goes to Needs you with that reason. No timeout while Claude Code's trust dialog waits on the person (a worktree Abe did not trust), nor for sessions an earlier `serve` launched (their hooks may have come while none listened).
- **Subagents**, ADR 0020 CC7). Every launch writes core's Claude Code plugin to `<plugins>/<id>/` (`$XDG_CACHE_HOME/abe/plugins`, else `<$ABE_STATE_DIR>-cache/plugins` beside an own state folder, so a serve of its own shares nothing with the default one, else `~/.cache/abe/plugins`: outside the state, which a session may not read, nor the default state folders beside an own one, `$XDG_STATE_HOME/abe` and `~/.local/state/abe`: `Locations.defaultStates`, `sessionBoundary`'s `defaultStates`) and passes it as `--plugin-dir` (`sessionPlugin` in `core/src/skills/subagents.ts`: `.claude-plugin/plugin.json` named `abe`, core's skills, `agents/reader.md` and `agents/writer.md`). `reader` (read tools plus `Bash` for `git diff`, `abe … show` and test runs, no Edit / Write / NotebookEdit: its prompt, and later Reach's permission rules, keep `Bash` to looking) wants Sonnet then Haiku, `writer` and the coordinator want Opus (`isolation: worktree`); each gets the first model it wants that the `allowedModels` in force in the checkout has, else the first allowed one, so an Override lowering it to `[sonnet]` puts all three on Sonnet. The settings carry the coordinator's `model`, `availableModels` = `allowedModels` (Claude Code then holds a per-call model to it too) and `worktree.baseRef: head`, so a writer's worktree (`.claude/worktrees/agent-<id>` in the main checkout) branches from the card branch. Core's instructions tell the coordinator to delegate (at most `subagents.max` at once, 4 by default) and merge each writer's branch with `git merge --no-ff`. Runs come from the hooks only: an Agent call's `PreToolUse` (its type, description and any model), `SubagentStart` (`agent_id`, `agent_type`) and `SubagentStop` (`last_assistant_message`) give `session.subagent` events (name, task, model, running / done, the result's first line) and `abe session show`'s `subagents`. A card's subagent running with no tool call for `SUBAGENT_SILENT_MS` (15 min) and no `SubagentStop` is silent: serve types into its coordinator once that it went quiet with no hand-back, its transcript named (`silentSubagents`, `silentTold`). The payloads carry no model: it is the call's (one `allowedModels` lacks runs on the coordinator's), else the model the session rendered core's agent on, else unknown. A `SubagentStop` with no type and no start is Claude Code's own helper and no run; `SubagentStop` leaves the session's state as it was (a background writer may end while it waits on you).
- **Transcript** (the platform facts are slice t113a's comment on it). `core/src/session/transcript.ts` turns one line of a session's Claude Code transcript JSONL (`entriesOfLine`) or one hook payload (`entriesOfHook`: `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, which come before the JSONL has the same call) into `TranscriptEntry`s (the same kind and id from both; a hook's result has the patch and a Bash's output, the JSONL's every tool's text): `user` (its implicit context split off), `assistant-text`, `tool-use`, `tool-result` (a file tool's `structuredPatch` as `patch`), `compact`; the same ids from both (`tool_use_id`, `prompt_id`), long texts capped, every other line dropped. `serve/src/session/transcript.ts` keeps one list per session: a hook's message never replaces one the JSONL gave (a message sent mid-turn comes with the running turn's `prompt_id`), its line takes the hook's place by id or, under another id, by its words and moves it to where the JSONL has it; each read's main and subagent entries go in by `at` (each file's own order), so the list after a `serve` restart is the one it had. `askedQuestions` reads AskUserQuestion's input. The transcript is for drawing only, the state stays the hooks'. `serve/src/session/transcript.ts` (slice t113b) follows each session's JSONL (its `transcript_path`, only when `isTranscriptPath`) and its subagents' `<session>/subagents/agent-*.jsonl` (entries tagged with the subagent) from the byte offset each reached, a partial last line left for the next read, on every hook (`UserPromptSubmit`, `PreToolUse`, `PostToolUse(Failure)` and `Stop` wait up to 2 s for it, so the list keeps the JSONL's order) and every 5 s, plus the hooks' own entries; one numbered list per session, an entry of a kind and id already there replaced in its place. Each batch is `session.transcript {session, from, entries}` events, one per run of numbers touched: a reader puts each entry at its number (`splice(from, entries.length, …)`). `abe session transcript <id> [--since <n>]` answers from `n`; refused `transcript-unreadable` when the file is gone or not the session's. The newest 5000 entries are kept in memory, read again from the files (no events) after a restart, numbered anew (hook-first entries and `changes` may sit elsewhere then), so a reader that sees a new `serve.started` reads again from 0. **Changes come from git**: at `UserPromptSubmit`, after each `Edit` / `Write` / `MultiEdit` / `NotebookEdit` / `Bash` and at `Stop`, the worktree is snapshotted without touching it (`RunTree.transcript.snapshot`: its index copied to a temporary one, `git add -A` there, ignored files and writers' `.claude/worktrees` left out, `git write-tree`), and the turn's files from its start snapshot to the newest are a `changes {turn, files: FilePatch[], cut}` entry (core's `patchesOfDiff` reads `git diff -U3`, at most 100 files), so a Bash `sed` and a merged subagent's work show; the snapshots are kept in `<state>/sessions/<id>/turns.json`. `abe session revert <id> --turn <user entry id> [--file <path>]` (a person's) puts the turn-start text back through a temporary index (a file new in the turn removed), refused `changed-since` naming the files that moved past the turn's end snapshot, `turn-running` while it runs. `core/src/session/steps.ts` is the step rows' verb table: a tool call and its result as `{glyph, verb, object, result}` (`Read api/src/cart.ts`, `Searched "quantity" · 4 files`, `Ran npm test · 1 failed · <first failing test>`), a Bash command read for what it does (`cat` / `sed -n` / `head` read, `grep` / `rg` search, a test runner's counts from its output). A box's sessions are read by the box's own serve, inside its workspace container through the same port (`containerRunTree`); its events reach the local machine through the merged watch, tagged `box`, and the local machine forwards `session transcript` / `revert` to the box (`CloudSessions.forward`).
- **Cards and Overrides** (slice t114a: serve's side). A session asks with Claude Code's own AskUserQuestion: serve answers its `PreToolUse` hook with a deny (`askDeny` in `core/src/session/ask.ts`: `Asked in Abe's Chat: <question> End your turn now; the answers come as your next message.`, printed by the hook client within four seconds) and keeps the questions as cards in the session's meta (`askCards`: the header, else the question's second sentence, as the why line; the recommended option first; several questions in one call a grill round, one card each), sends `session.ask`, and the turn's `Stop` leaves the session waiting (`sessionStep`'s question cards; no Notification fires). `abe session answer <id> --card <card> (--option <n> | --text <words>)` (a grill: `--option` once per card or `--answers '[1,"own words",3]'`; a multiSelect question's options, `AskCard.multi`: `--option` once each alone, a list in `--answers` (`[1,[1,3],2]`) and `--pick` (`2:[1,3]`), sent as `1 <label>, 3 <label>`; one question's pick before the round goes, `--pick <n>:<option|[options]|"own words">`, is kept on its card as `AskCard.picked` in the meta and said as `session.ask`, so a restart, a second client and Reopen show it: Chat sends each pick as it is made) clears the cards, types the answer as the next prompt as `session send` does (`Answer to "<question>": 1 <label>`; a grill one numbered message) and sends `session.answered`; a prompt typed in Terminal mode clears them too (answer null). `abe session asks <id>` lists the open cards. `abe session override <id> --what <area> --reason <text>` (`core/src/layer/override.ts`: a Reach area `db|aws read|write <env>`; a write refused `writes-only-on-box` on a local session; `network <host>` is no area since the network is open (ADR 0029), and one an older serve kept is dropped on read) keeps the Override in the meta until the session ends (no comment on the story: `story` says `NOT_COMMENTED`), puts its line in the open pull request's `## Notes` (else `abe factory pr` does), sends `session.override`; `session show | list` carry `overrides`. While one lives, a `PermissionRequest` in its area (its command names the area's Reach name, AWS profile or host: `inArea`) is held for a permission card (`serve/src/session/ask.ts`, `Holds`): Allow once (recommended when sandboxed or inside the worktree) · Allow for this session (the same tool and input allowed at once after) · Deny · own words (deny with them), answered through `session answer`; past `PERMISSION_HOLD_MS` (600 s; the hook waits up to 615 s, Claude Code 630 s for it, `PERMISSION_HOOK_TIMEOUT_S`) the hook prints nothing, Claude Code's own dialog stays and the card says `Answer in Terminal mode · ⌘4`. Any other `PermissionRequest` a person answers (an ask rule's, one outside every Override) gets that card at once, its tool and command in its title, never held; it goes once the tool runs or is denied, a prompt is typed or the turn stops. A box's session keeps its cards and Overrides in the box's serve; the local machine relays `answer`, `asks` and `override` there (`CloudSessions.relay`).
- **Who is asking.** Each session has its own socket, `<state>/sessions/<id>/session.sock`. A request on it is dispatched as `caller: 'session'` with `ctx.session` = that id (undefined on `serve`'s own socket): rows with `inSession: false` are refused `not-in-session`, and a handler naming another session refuses `not-your-session` (`yours` in `serve/src/session/sessions.ts`). A client on a session socket never starts a `serve` (`isSessionSocket`). A command from a session acts on its own run only (`serve/src/session/own.ts`): `card comment | tag | move` and `sheet attach` on its own card, `issue create` and `pr create` in its worktree's origin repo, `pr create` from its own branch, `pr update` on that branch's pull request, all else `not-your-session`; the board comes from its own checkout's settings, not the request's `cwd`, every settings read is its own checkout's, and a file it names (`--body-file`, `--report`, `--file`) must lie in its worktree or checkout once links are resolved. `session send` is a person's only (`inSession: false`): a prompt typed into the pane is the person answering Needs you. A person on `serve`'s socket is not limited.
- **Boundary** (ADR 0020 CC6, `sessionBoundary` in `core/src/session/session.ts`). The settings turn on Claude Code's sandbox for the session's shell: `failIfUnavailable` (no sandbox, no `claude`), `allowUnsandboxedCommands: false` (no retry outside it, and a repo's settings cannot loosen it), commands inside it run without a prompt. Neither a file tool nor a command writes a `.claude/settings.json` or `.claude/settings.local.json` (`PROJECT_SETTINGS_DENY`), so the agent adds no hook or allow rule of its own (the managed-only keys a box uses do not exist for `--settings`). It hides the state directory (`serve.sock`, `tmux.sock`, every other session's folder) but `<state>/bin` and the session's own folder, connects to no Unix socket but the session's own, writes its worktree, its writers' worktrees (`<checkout>/.claude/worktrees`) and the package caches (`SANDBOX_CACHES`), never the state, the plugins, the checkout's `.git/config`, `.git/hooks`, its own and its worktrees' `config.worktree`, where each worktree's repository is (its `.git` file, where the runner really put it too, `commondir`, `gitdir`, the main checkout's `commondir`) nor a submodule's (any depth) config, `config.worktree`, `commondir` and hooks (all of which `serve`'s own git would run, outside the sandbox); the network is open, any host outbound (ADR 0029: these lists become Abe's own Seatbelt jail, Claude Code's sandbox off; `SANDBOX_DOMAINS` and `strictAllowlist` stand only for a runner with no jail); the Keychain's services are the only lookups refused, so the agent's own `gh` verifies TLS through trustd. Deny rules keep Claude's file tools out of the same places (`Read` / `Edit` the state, `Edit` the rest), and refuse a merge or a branch written through GitHub's API (`gh pr merge`, `gh api` merges, refs, contents, `mergePullRequest`, auto-merge, `gh alias`: `MERGE_DENY`), the repository's branch protection, rulesets or default branch changed (`gh api` `protection`, `rulesets`, `BranchProtection`, `default_branch`, `gh repo edit`), a `gh api` request read from a file (`=@file`, `--input`) and the session worktree's hooks turned off (git's config on its line, `git -c` / `git … -c k=v` / `--config-env`, or in `GIT_CONFIG_*`, `hooksPath`, `--no-verify` however short) as commands (`SESSION_COMMAND_DENY`; to give each worktree its own `core.hooksPath`, the runner turns on the repo's `extensions.worktreeConfig`, so git reads `.git/config.worktree` in the main checkout too, which no session writes; a box's session gets `MERGE_DENY`). No deny rule can say "all but the worktree", so serve answers the PreToolUse of Claude's own Write, Edit, MultiEdit, NotebookEdit and WebFetch (`core/src/session/fence.ts`, `serve/src/session/ask.ts`, the hook waits up to four seconds for it): a write whose real path (a link followed, one to a path not there yet too) is outside the worktree, the card's Before worktree (`<worktree>-base`), the writers' worktrees, the caches, `~/.claude/plans` and the sandbox's `/tmp/claude`, or is in any `.git`, or is Claude Code's own config in the worktree (any `.claude` folder, `.mcp.json`, any case: a skill's, agent's or command's frontmatter hooks run outside the sandbox; the shell's sandbox refuses those too), or is a file with another hard link, is denied, and so is a Skill named `<dir>:<name>` that is a `.claude/skills` in a folder of the worktree (a folder moved in from `/tmp/claude` brings one past the sandbox; a nested skill Claude Code offers by its bare name is not caught) (`Write refused: outside this session's worktree (…), the only place its tools write: <path>. …`), and so is a WebFetch to a host the shell does not reach (none while the network is open, ADR 0029); a step row shows the reason without Claude Code's `PreToolUse:<tool> hook error:` prefix; a serve that does not answer in time (or is gone) gets the tool refused by the hook (`FENCED_BY_ABE=1` in the session's environment), never let through unchecked, and so is a fenced tool whose payload the hook could not read whole in time; a link a running shell swaps in between the check and the write is not caught (the file tools run outside the sandbox); the session keeps no auto memory (`autoMemoryEnabled: false`: it would be written under `~/.claude/projects`). Claude Code reads the `--settings` once, so an Override cannot open a host to the shell of a running session: `session override` says so in its `shell` line. Each Abe worktree runs core's session hooks (`core/src/session/session-hooks.ts`, installed by `ports/src/git/worktrees.ts`: its `config.worktree` `core.hooksPath` on `<git>/hooks/abe-session`): a push to the default branch is refused `abe: default-branch-push: main is the default branch, and a session never pushes to it. …`, every other hook the repository has (its `core.hooksPath` in any other scope, else `hooks/`) runs as before, but `reference-transaction` and `post-index-change` (git runs them on every ref and index change); the hooks are written through a rename, and left alone when unchanged. Defence in depth, no wall: a script, or a clone with gh's token, may still push. A push to `main` / `master` named on a line, any push in the main checkout, `gh api … mergeBranch` and `gh auth token` are refused as commands too; Before's worktree gets the session hooks. Serve's own gits run with `core.fsmonitor=false`, no submodules (`SAFE_GIT_CONFIG`, `ports/src/mac/process.ts`): a nested repo's config the shell writes runs nothing there (a submodule's moved pointer is not in Before's diff then). In a repo that commits `.claude/` files, a shell `git pull` / `rebase` / `checkout` that changes them fails part-way (the sandbox holds every `.claude`): the session says so and the person takes it. An agent set on getting out still can, through what serve runs from the worktree outside the sandbox by design (checks, `abe run`, the repo's hooks on serve's push): the boundary holds an agent's mistakes and the auto classifier, not a determined attacker. The caches the sandbox writes are the package managers' own (`SANDBOX_CACHES`), not all of `~/.cache` / `~/Library/Caches` (a poisoned entry in those package caches would still reach the person's own installs: accepted, as npm and pip check content hashes). Paths are real paths, as Claude Code matches them. Hooks run outside the sandbox, as Claude Code runs every hook. MCP servers (`session.mcp`, `claudeArgv`): a repo's own servers (its `.mcp.json`, approved in the checkout or not) never load in any session kind, Connected included. A local chat of yours (Ask, Improve, a prototype chat) loads Abe's and, by default, yours (`yours`: your user-scope servers, the `mcpServers` of your `~/.claude.json`, named with `--mcp-config` while `skillsOnTop` is off, since `--setting-sources project,local` leaves them out: `personalMcpConfig`, the file itself, never a copy; a server added for one folder only, `-s local`, is not the worktree's; and your claude.ai connectors). It is not `--strict-mcp-config`, so its settings reject the repo's (`withRepoMcpOff`: `enableAllProjectMcpServers: false` and `disabledMcpjsonServers` naming each server of the worktree's `.mcp.json`, read by name only), which Claude Code honours in every permission mode (its docs: an entry in any settings file still rejects the server). Every other session is `--strict-mcp-config`. They start in the session's environment (the allowlist, its `PATH`), not your shell's, so one that needs more fails to start there. Their tools run outside the sandbox and aren't checked by Abe's fence: by design for a local session, not a gap. To restrict, `abe settings set session.mcp abe-only` (Settings › Agents & models › Sandbox), or the repo's settings set it: `--strict-mcp-config` and only Abe's own servers (none for a plain session). Tightening is free; below a Layer's `abe-only`, `yours` is a personal Override with its `--reason` (ADR 0010). A card's session (a Factory run's, its browser's too), an install's and a box's load Abe's own and the repo's sources alone, whatever the setting says. Locally (ADR 0027, `core/src/install/source-servers.ts`, `SessionRunner.sourceServers`) they are the main checkout's Claude Code local servers (`projects[<main>].mcpServers` of your `~/.claude.json`; the session's folder, a folder in it, a card worktree beside it and a linked worktree all resolve to it, a sibling checkout not), then your user scope's for a `sources:` name the checkout has none of (the checkout's install's added sources count as such names, `installSources`, so one removed from the local servers since is missing as a `sources:` one is), of those only each whose check at the install's Sources passed (connected, its one read ok: `checkedSourceServers`; none before Sources is done; an unchecked one told as not checked at install), every session's `claude` with `MCP_TIMEOUT` 15 s: each definition copied as it is (name, URL, headers, so Claude Code's stored sign-in is reused) into a config Abe generates, `<state>/sources/<id>.json` (mode 600, out of the sandbox's reach, removed at stop), named with `--mcp-config` before Abe's; a definition with a header or env value that is no `${VAR}` reference is withheld, never copied. On a box (3.2.1, box parity) each source comes from the Mac's synced `abe.yaml` `sources:` with its definition (a bare name is missing there), of those the Mac's install checked (`session run --sync`'s `checked`), in a config Abe generates in the session's folder (`sources.json`, never the box's own Claude Code config), signed in with the Mac's access token the sync merged into the box's Claude Code store under the Mac's key (`core/src/box/box-sync.ts`). `allowedMcpServers` in the session's settings, so no other server of it starts. A source no scope names (one in a repo's `.mcp.json` alone, a claude.ai connector only) does not load: the session is told in its instructions (`sourcesTold`: one line naming only those that loaded, then which did not and why), and says so to you at its start; `session show` says `sources     not loaded here: …` (`sourcesMissing`). A plain session's `abe-only` loads no source. Linux's sandbox allows every Unix socket or none, so a local session launches only on macOS (`no-sandbox` elsewhere).
- **A local run's verify**. What a box's workspace does outside the sandbox, the local machine's `serve` does for a local session. `abe run <script> [args…] [--env dev|test|prod]` (an environment off for agents refused `env-off`, ADR 0029) from the session (`serve/src/local-mode/local-apps.ts`) runs the Verification pack's script in its worktree, or Before's by its absolute path (`<worktree>-base`; `runScriptIn` in `core/src/repo-hooks/`, by the main checkout's committed `abe.yaml`), to its end in a process group of its own with `APP_ENV` of serve's environment (no token), the session's database and its mark `ABE_APP_OF=<id>` (`core/src/session/session-apps.ts`; output under `<state>/sessions/<id>/apps/`, the group and worktree kept in `apps.jsonl` there, `ports/src/mac/session-apps.ts`). `abe run stop` runs the pack's stop script, then stops the groups kept for its worktree from serve, so a session never signals what `abe run` started (its sandbox refuses it). The session's database is had in the checkout before `claude` (`dbNeed`): the repo pack's hook `.claude/skills/run-app/scripts/db` (idempotent; `start` prints the URL last, `ABE_DB_NAME=abe-db-<id>`), else its own `abe_<session>` in Abe's local database when its pack, env example, `.abe/abe.dev.env` or CI says `DATABASE_URL` (serve's own never): its URL is in the session's own environment (its jail's shell, its writers), its checks' and its `abe run` scripts' in dev (`takesOwnDatabase`: over `.abe/abe.dev.env`'s; in test or prod that environment's file's); a failing hook refuses the launch `no-database` with its output and the cloud target as the way out; with no Docker, a Factory run is refused `no-docker`, its checks would go red for want of one, and any other session is told it has no database and never to ask for one (`NO_DATABASE_NOTE`). When the session ends, its browser stops, the pack's stop script runs once in each worktree a script ran in, each kept group gets TERM then KILL, then every process whose environment holds the session's `ABE_SOCKET` or mark (`ps -axwwE`, `leftovers`: never by folder, VimStorm's own shells sit there too), and `db stop` runs. At each turn's end, each run step's end and the run's (no subagent running), and the session's end, serve's own git tidies its merged writers (`Git.tidyWriters`): a writer worktree whose head the card branch holds is removed (one under the card worktree's `.claude/worktrees`, or one of the session's own subagents under the main checkout's, where Claude Code makes them; one the session's own `git worktree remove` left with only deletions goes with `--force`), the record of a writer whose folder is gone removed once the card branch holds its branch (till then kept, so a later tidy still finds the branch; never a `git worktree prune`, which would forget it), every other worktree's stale record (its folder gone, not locked, no writer's of any session) pruned, and each such `worktree-agent-*` branch deleted; an unmerged one is never touched.
- **The Verification pack**. The repo's own skill `.claude/skills/verify-<app>/` (`<app>` the checkout folder's name; `core/src/factory/verification-pack.ts`): Launch, Doctor, Drive, Evidence and Cleanup, and a Feature map of every user-facing feature (`features/README.md` grouping them, the most used first, and linking one file per feature, four H2s each). A run's Verify drives the features the change touches through it, a web app with headless Playwright in its own browser against the local app only, its helpers run by `abe run .claude/skills/verify-<app>/scripts/<name>`; `abe factory verify --phase after --result pass` on a worktree with a Feature map is refused `feature-not-listed`, `feature-unknown`, `feature-unjudged`, `feature-unproven` (a driven feature without a screenshot and a recording in `.scratch/<card>/`; a feature whose surface is `cli` or `api`, said in its feature file's front matter (`surface: http` is an api) or else in the pack's: a screenshot or a transcript, `.txt`, `.log`, `.cast`, `.json`; the refusal names the feature's surface, what proves it and how to declare another) or `not-driven-no-reason` until its `## Features` says every mapped feature, and `no-verify-html` without `--html` or `feature-html-differs` (naming each feature) while the HTML report's sections (`data-feature`, `data-verdict`) are not those features with those verdicts. maintain-verification-skill keeps the map true on the card's branch. The pack is found in the run's worktree by its folder (`RunTree.folders`), on a box's clone too. A session's `abe run`, local or on a box, runs one script at a time (`one-runner`; `stop` always runs), and a local repo whose app takes fixed ports (`ports.fixed` in `abe.yaml`, or what its install read fixed) runs one session's app at a time: another session's `start` while one holds them is refused `ports-held`, naming the holding session and card, until it runs `stop` or ends; and a script that may run docker compose gets its card's own project (`COMPOSE_PROJECT_NAME`, `abe-<repo>-<card>`, Before's `-base`; the ports inside left as the compose file has them) on the local Docker only: a remote `DOCKER_HOST` (its own or a compose `.env`'s) or docker context is refused `compose-not-local` before it runs; the session's end takes each project down (`core/src/session/compose.ts`, `ports/src/docker/compose.ts`). On a box (no Docker in a workspace, never the box's socket in one) a pack script's `docker` is a shim (`DOCKER_SHIM`, first on its `PATH`) that hands `docker compose` to `abe compose --cwd <dir> -- <args>` on the workspace's socket: the box's serve reads the compose file in the workspace, runs `docker compose --project-name abe-<repo>-<card> --project-directory <the clone> -f -` on the box's Docker, `<the clone>` the workspace volume's mountpoint when the box host can read it (`Docker.volumePath`), else a copy synced into `<state>/compose/<project>` before a start (no `.git`, no `node_modules`, said in its output), so build contexts and relative mounts are the clone's; an absolute host path or one up out of the clone is refused `compose-path-outside` by file and line (`composePathsOutside`) (refused `compose-not-local` as locally; `-p`, `-f`, `--context` and the like refused `compose-args`), joins the workspace container to `<project>_default` after a start and takes it off before a `down`, and takes the card's projects down when its workspace is removed. A host port a compose file publishes as a number is warned of with the run (`RunData.warning`, `<file>:<line>`): the pack publishes from `ABE_PORT_BASE` or not at all.
- **Commands.** `session launch | list | show | send | answer | asks | override | transcript | revert | attach | stop`, and `hook` (answered only on a session's socket). `send` pastes the text and presses Enter; `attach` without `--json` runs `tmux attach` on your terminal (a session's tmux draws no status line), and for a cloud session `abe box attach <box> --session <id>` (ADR 0021: SSH through the box's EC2 Instance Connect Endpoint, a reconnect loop around tmux there).
- **Messages, implicit context, model** (`serve/src/session/queue.ts`, `core/src/session/context.ts`). `session send <id> <text…> [--context <json>]` builds the prompt with its implicit context (`messageWithContext`: a selection `{path, from, to[, lines]}` as `Context: <path> lines 12–18` and its lines fenced, at most 200 with `… N more lines`, read from the worktree when not given; the caret `{path, line}`; a card `{card, title}` as `Context: story #2 …`; none after a `/command` or `!` shell input, which run as typed); `splitContext` / `contextChip` read it back for the transcript's `user` entry (every block taken out of a queue sent as one prompt). A message is typed in as you send it, mid-turn too: Claude Code keeps it in its own queue and takes it at the agent's next step (with the next tool result: its `UserPromptSubmit` as it is typed, then a `queued_command` attachment in the JSONL, which the transcript shows once, there; a long paste's `<pasted_content>` marks are taken off). `serve` holds one back only while the session cannot take it (`HOLDS`, the answer's `held`, its `queued` the `n`; never a `/command`, which goes at once and without context): `starting` (launched, its `claude` has not taken its launch's prompt yet: keys typed before it would wait for the whole first turn, or land in the trust dialog), `dialog` (a permission prompt or elicitation in its terminal, `waitingOn: dialog`: keys would answer it) and `question` (a question card asked while the turn still ends). Held messages are kept in `meta.json`, shown by `session show`, a `session.queued` event per change, `session unqueue <id> <n>` takes one back; at the first hook that frees the session they are typed in as one prompt, a blank line between (whether it may go is looked at again just before the paste, and a PermissionRequest / Elicitation hook is answered only once a paste on its way in has its Enter in, so no Enter lands on the dialog); a `/command` is refused while `starting` or `dialog`; a restarted serve holds a session with no transcript yet and types in what it held once the session is free; one paste at a time per session (they share its tmux buffer). Verified against Claude Code 2.1.310 in tmux (`.scratch/2.2/i197`). `session model <id> --model <m> [--effort low|medium|high]` opens Claude Code's `/model` picker (`/model` alone; `/model <name>` and `/effort` would save it as the person's default in `~/.claude/settings.json`), reads it from the pane (`core/src/session/model-pick.ts`), moves to the model's row (a session's `modelPicker` setting lists its `allowedModels` by name) and the effort with ←/→, checks the focus, then presses `s` (this session only), the picker closed with Esc when it fails, held to `allowedModels` at launch and now, refused while a dialog waits; `model` / `effort` are in `show` / `list` (launched on the coordinator's model and the `effort` setting as its `effortLevel`; a resumed one keeps its own), each change a `session.model` event.
- **Setup.** A card's new worktree is made ready by serve, outside the sandbox, before `claude` starts (`prepareWorktree`, `ports/src/mac/worktree-setup.ts`; rules in `core/src/session/setup.ts`). First what the checks need is copied in from the main checkout when absent (`worktreeCopies`): the files Local only kept out of git (`.abe/`, its agent files) and each untracked env file of the top and the workspaces Read found whose keys are all public (`publicEnvOnly`, as the never-read rules read them) or that is named for tests (`.env.test*`, `.env.unittest*`, `.env.ci*`: `testEnvFile`, whatever its keys; the setup line names its keys, never a value: `copied .env.unittest (keys DATABASE_URL, API_SECRET)`), never one with cloud credentials or aws in its name. Then its packages. When its lockfile (`LOCKFILES`: package-lock, shrinkwrap, pnpm-lock, yarn.lock, bun.lock(b)) is byte for byte the main checkout's and the checkout has its packages installed, each `node_modules` of the checkout's (the top's, and each folder's with a tracked `package.json`) is mirrored entry by entry: a third-party package (and pnpm's `.pnpm`) is a link to the checkout's, which the sandbox keeps the session from writing; a link into the repo's own folders (`node_modules/@acme/ui` → `../../packages/ui`, a workspace's `node_modules/@acme/ui` → `../../../ui`) points into the worktree, so a change to a shared package is the one its checks test; `.bin` is a folder of the checkout's links read again in the mirror, so `npx`, `.bin` and package scripts find each tool, the repo's own ones in the worktree; the other dot entries (`.vite`, `.cache`, npm's `.package-lock.json`) are not shared, so tools write their own (a fixture monorepo in `worktree-setup.test.ts` proves it, `npx` included); then the `setup` setting's other steps run as a setup does (`setupAfterLink`: its steps split at `&&`, `;` and line ends outside quotes, those whose first command is a package manager's install, `npm ci|install|i`, `pnpm install|i`, `yarn [install]`, `bun install|i`, left out, the rest joined by `&&`; none left: nothing runs), so codegen still happens. Else the `setup` setting (a repo pack's command, `setup: npm ci`; read in the checkout, never a worktree), or with none the lockfile's own install (`ciCommand`: `npm ci`, `pnpm install --frozen-lockfile`, `yarn install --frozen-lockfile` or `--immutable` with a `.yarnrc.yml`, `bun install --frozen-lockfile`), runs through `/bin/sh -c` with the session's environment in the worktree (`SETUP_TIMEOUT_MS`, 15 min), its network the package registries alone: `sandbox-exec` lets it reach only a proxy of serve's on 127.0.0.1 (`registryProxy`, every package manager's proxy variables set; Cypress', Puppeteer's and Playwright's binary downloads skipped, `CYPRESS_INSTALL_BINARY=0`, `PUPPETEER_SKIP_DOWNLOAD`, `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD`: their binaries are in the person's cache, shared with the main checkout), which tunnels to the public registries (npm, yarn, PyPI) and those the main checkout's or the person's `.npmrc`, `.yarnrc.yml`, `.yarnrc` and `bunfig.toml` name (`registryHosts`; never the worktree's, which the agent writes) and answers any other host 403, named at the end of its output. Once it passed there (`abe-setup` in the worktree's git folder) a later launch does not run it again; one that failed or was cut short runs again. `abe session show`'s `setup` line says what was done (`setupText`: `packages linked from <checkout> (the same lockfile) · copied .abe, .env.test`, or `npm ci (network: the package registries only): passed`); a failed one puts a Factory run at Needs you with its command, exit and the end of its output (`setupReason`), and `claude` starts all the same so the person answers in Chat. A local card session gets the `NODE_OPTIONS` the repo's CI gives (`ciNodeOptions`, read in the main checkout), so its tests have the memory they have there. A box's `abe workspace up` does not run it yet.
- **The worktree recipe** (`worktree:` in `abe.yaml`, the team's; `core/src/session/worktree-recipe.ts`, ADR 0032). ## One-shots

A small ask answered by `claude -p` in one go: no tools, MCP servers, slash commands or settings files (so none of your hooks), nothing kept (`oneShotArgv` in `core/src/triage/one-shot.ts`); the prompt on stdin, the answer its text. The port is `OneShot` (`ports/src/claude-code/one-shot.ts`: killed after 3 minutes, `one-shot-timeout`; `no-claude`, `one-shot-failed`). `serve/src/layer/one-shot.ts`' `askOneShot(ctx, { role, cwd, prompt, system })` runs it as a role (`ROLE_MODELS`: coordinator and writers Opus, readers Sonnet then Haiku), on the first of the role's models that `allowedModels` allows (else its first), in a session's clean environment (with the Reach a session there gets, `sessionReach`) without its socket (`oneShotEnv`). Ask for JSON with `askingJson(prompt, shape)` and read it back with `readJsonAnswer(text, schema)` (zod; the JSON may sit in a fence or between lines). Tests: the fake `claude` answers `-p` from `scriptOneShot(home, { answers })` and logs each call (`oneShotCalls(home)`).
