# Part: sources

Optional. Passes when each source found is added and reads, or is skipped. The team's list is a team part; each person's sign-in is theirs, so on a join only the sign-ins are left.

A source is what the repo's sessions read besides the board and GitHub: Sentry, Figma, Slack, an MCP server the repo names. Every source is the team's: its MCP server goes in `abe.yaml` `sources:` (name, URL, transport; never a secret). Abe hands the sources to every session of the repo (the install's, cards', Ask's) through its generated MCP config, and teammates who pull the repo get the same set. Each person's sign-in stays in their own Claude Code, which keys it by the server's name and definition, so a definition the person had already reuses their sign-in.

1. Run `abe install sources --json`. It lists the repo's `sources:`, then each server the person's Claude Code has (this checkout's local scope, then the user scope) that `sources:` does not define, marked `found: local-scope` or `user-scope`. The sources Read found and not yet added or skipped are named by `abe install check sources`'s line (`sources-unanswered`), each with why it was found.
2. **Which to add is an up-front question** (multiSelect): each found source with why it was found, the ones the repo uses recommended, and **Not sure: find out**. A `local-scope` one moves into the team's `sources:` so teammates get it too.
3. **Add**: `abe install source <name>` (a server the person's Claude Code has, copied as it is; one `sources:` defines already; or one Read found, on the server known for it), or `abe install source <name> --url <its MCP server's URL>` (https, or http on localhost; `--transport sse` for an SSE one; `--transport stdio --command <cmd> [--arg <arg>]…` for a local one; an argument that starts with `-` as `--arg=-y`) for one with no server known, or one the person names at any time. It writes the server into `sources:`. A literal header or env value is refused: no secret goes in the repo. **Skip**: `abe install source <name> --skip` for one Read found the person does not want; it stays out of `sources:`.
   - **A server that needs a secret** (an API user and password, a token: a local server with no sign-in of its own) is added by reference: `--env <KEY>` for each key a stdio server reads, `--header <Name>=<VAR>` for an http one. `sources:` holds `${KEY}`, never the value. A server the person's Claude Code has with the value in it is refused `source-secret`: add it by its definition instead, the same command and arguments, each value as `--env`.
   - **Each person's value** goes in their `.abe/sources.env` (`KEY=value` a line; out of git, synced to their boxes). Abe fills it into the session's generated MCP config at start, never into the session's env. Write the file with the keys and empty values yourself, then ask the person to fill them in their editor: `! open -t .abe/sources.env`. Never print, quote or echo a value back; when they paste one in the chat, write it into the file and never repeat it. Never read their other servers' values.
4. **Sign in**: an added source that needs a sign-in: run `abe source sign-in <name>`. serve runs the server's own sign-in in the person's browser, outside any session (no token pasted), and checks one read. Tell the person in one line that their browser opens, and go on with another part meanwhile. Never start a sign-in another way: no MCP `authenticate` tool, no `/mcp`.
5. **The live read**: `abe install connection` reads each added source where a session in this checkout loads it (connected, or its sign-in) and, connected, its probe: one reading tool call (`Read`: ok; failed when the account can't read it; a warning when it gave no answer in time) and the account it is signed in as (`Account`, `Org`, `Project`, as far as the server told). A connected source with no account rows is still ok.
6. Then `abe install check sources`. A `${KEY}` with no value in `.abe/sources.env` fails it `source-value-missing`, naming the key. Its line names a source not answered, or one that does not read: the sign-in failed (Claude Code too old: the person updates it), its server does not answer (down, or a wrong URL), or the account can't read it (sign in again as another account).

## Feature flags

When the repo uses a feature-flag service, offer its MCP server as a source, preselected, so agents read a flag's state instead of asking the person. Look for the SDK in the lockfiles and imports, and its keys in env examples:

| Service      | Seen as                                                              | Its server (official)                                                                                                                                                                                     |
| ------------ | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ConfigCat    | `configcat-*` SDKs (`@configcat/sdk`, `configcat-js`), `CONFIGCAT_*` | stdio only: `--transport stdio --command npx --arg=-y --arg @configcat/mcp-server --env CONFIGCAT_API_USER --env CONFIGCAT_API_PASS` (Public Management API credentials, not an SDK key)                  |
| LaunchDarkly | `launchdarkly-*` SDKs (`@launchdarkly/*`), `LD_*`, `LAUNCHDARKLY_*`  | hosted, OAuth: `--url https://mcp.launchdarkly.com/mcp/launchdarkly`, then `abe source sign-in`. Not on the EU or federal instances: there, stdio `@launchdarkly/mcp-server` with `--env LD_ACCESS_TOKEN` |
| Unleash      | `unleash-client`, `@unleash/proxy-client-*`, `UNLEASH_*`             | stdio: `--transport stdio --command npx --arg=-y --arg @unleash/mcp --env UNLEASH_BASE_URL --env UNLEASH_PAT` (a personal access token). Its remote server is in beta, Enterprise plans only              |

An SDK key in the repo's env files is no server credential: never put one in `sources.env`. Each server's tools write flags too, and a session may call every tool of a source: say so in the question.

## After the install

The person may ask for a source any time later (from the Abe chat, or `/abe:improve`): do steps 3 to 6 for that one source. A source added later is checked like one added at the install: until `abe install check sources` passes for it, no session starts its server.

Never run `claude mcp remove`: a server in the person's Claude Code stays there, with the sign-in it shares. Never read, copy or print a server's token, header or env value. A claude.ai connector does not count: card sessions never load connectors.
